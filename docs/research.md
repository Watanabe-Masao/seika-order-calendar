わかったこと

- 翌年分は、毎年**10月中旬〜11月中旬に1日でまとめて**登録される（ここ4年は10/26〜11/18）。
- 全件が**終日・1日単位**の予定。複数日にまたがる予定、繰り返し予定、キャンセル済みの予定、同じ日の重複はない。
- 登録後に書き換えられた例はごくわずか：2024年分で1件（2023-11-25）。2021年分の一括更新（2026-04-04）は日付の変更を伴っていない。
  - → 年の途中で変わることは少ないが、ゼロではない。**毎週差分を取る**方式なら拾える。

## 3. GitHub Actions側の制約

- **公開リポジトリでは、60日間リポジトリに動きがないと、スケジュール実行のワークフローが自動で無効になる**（GitHub Docs）。
  - 休市日データが変わるのは年1〜2回なので、そのままでは止まる。
  - 対策の候補：(a) 月1回、状態ファイル（最終確認日時）をコミットする、(b) 無効化を防ぐkeepalive用のアクションを使う、(c) 非公開リポジトリにする（ただしPagesは有料プランが必要）。
- 公開リポジトリなら、標準ランナーの利用は無料。
- cronはUTCで指定する（JSTより9時間遅れ）。
- スケジュール実行はデフォルトブランチでのみ動く。

## 4. 判断が必要な点（実装前に決める）

1. **12/31「セリはありません」「卸のみ休業」の扱い**：仲卸は営業している日。発注先が卸だけなら休み扱い、仲卸からも仕入れるなら開市扱い。→ 現状は「休み扱い」で計算している。
2. **市場が休みの日に発注するか**：現状は「翌日が開市なら、当日が休市でも発注できる」としている。
3. **公開範囲**：Pagesで公開する（URLを知っていれば誰でも見られる）か、非公開にするか。
4. **データの検証**：高知市の公式PDF（色分け）は機械で読み取りにくい。年1回、人が照合する前提でよいか。

## 5. 構成案（次の段階）

```
.github/workflows/update.yml   # 毎週月曜 JST 6:00 / 手動実行
scripts/fetch.py               # 2本のicsを取得 → data/raw/*.ics
scripts/build.py               # 休市日・発注日を計算 → data/calendar.json
docs/index.html                # Pages。calendar.json を読み込んで表示
data/status.json               # 最終確認日時・データの最終日（keepalive兼用）
```

- 差分があったときだけコミットする。データ量が急に減った場合（例：前回の5割未満）はコミットせず、失敗として通知する。
- 12月1日の時点で翌年分がなければ、Issueを作る。
